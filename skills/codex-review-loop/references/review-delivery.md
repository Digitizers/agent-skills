# Review delivery and collection

### ⚠️ The review-object / inline-comment race — this WILL bite you

Codex posts the **review object first** (state `COMMENTED`, body = a generic *"💡 Codex Review — Here are some automated review suggestions"* wrapper) and its **inline review-comments land seconds-to-minutes later**. A poll that fires inside that window sees *a review at HEAD with zero inline comments*, which looks exactly like a clean pass. **It is not.** Merging there ships the findings unfixed — including P0/P1s.

- A review whose body is the **generic suggestions wrapper means findings exist**. Go find them. An empty inline list at that moment is a race, not a verdict.
- **An empty or unchanged poll is not a verdict.** Wait for an explicit clean verdict for current HEAD, or for actual findings from the current HEAD review to arrive and remain stable across two complete polls ≥90 s apart. Compare record IDs **and content/update metadata** on all three surfaces: new IDs distinguish re-posts; edits can change an existing finding without changing its ID. A generic wrapper plus an empty finding set, even twice, is still pending. Stability helps detect delivery; it never proves resolution or guarantees that a delayed comment cannot arrive. Re-fetch before handoff.
- **Always `--paginate`, on ALL THREE surfaces, including reviews.** `pulls/N/comments` (inline) pages at **30**, and `gh pr view --json comments` silently truncates to `comments(first: 100)` — so its `last` is not the newest comment on a busy PR. Read the verdict from `gh api --paginate repos/<o>/<r>/issues/<PR>/comments` instead. In a multi-round review the newest blocking finding routinely lands past page 1, so an un-paginated fetch reads a converged PR that isn't one — the same false-convergence failure wearing a different disguise.
- **Collect full bodies without filtering by commit, line, author, or severity.** Fetch *all* of `pulls/N/comments`, `pulls/N/reviews`, and `issues/N/comments`. A `line == null` comment may be a file-level finding (`subject_type == "file"`) or an outdated line anchor; neither proves that the defect is fixed. Review summaries and issue comments can contain substantive findings too. Filter only for navigation after saving the complete evidence, never to decide what needs triage.
- **`commit_id` and `line` are re-anchored; `original_commit_id` and `original_line` are not.** GitHub moves an inline comment onto the current HEAD as the branch advances. So `finding.commit_id == HEAD` does **not** mean the finding is fresh — it may be an already-fixed comment that followed you. Use **`original_commit_id`** as the "raised at" anchor (REFERENCE §3), and treat an **unchanged comment `id`** as "the same record", not "already handled", even when its line moved.
- **Ancestry proves CURRENT, never STALE.** `original_commit_id == HEAD` ⇒ current, triage it. But an *older* `original_commit_id` only says some commit landed after — not that it touched this code, and not that it fixed the bug. An unrelated push, or a fix that missed, leaves the defect live. **Auto-skipping on ancestry is how you ship the bug Codex handed you.** When the anchor predates HEAD (including `line == null`), **read the code at HEAD** — that is the only thing that settles it.
- **Empty evidence and failed collection must stay distinct.** On a findings-only PR there may be no Codex issue comment. A command that prints nothing can hide either that absence or a failed query. The complete snapshot in REFERENCE §2 records empty arrays explicitly and exits nonzero on collection failure; neither outcome is a clean verdict.
- **Poll surface (c) in the same breath as (a).** A clean pass emits *only* an issue comment — no review object, no inline comment. If your poll watches inline findings alone, a green PR looks "still in review" forever and you never converge.
- **Select records only after collecting the full history; never `tail` raw body text.** Codex bodies are multi-line, so tailing physical lines can drop the finding or verdict. Read full bodies; selecting the latest verdict for navigation does not excuse skipping earlier unresolved findings.
- **Make sure your poll command actually runs.** `gh`'s built-in `--jq` accepts one jq expression, **not** jq CLI flags like `--arg` — passing it exits 1 and the check fails *silently*, so you read "no verdict" forever. Pipe `gh`'s JSON into the real `jq` binary. A convergence check that can't fail loudly is worse than none.
- **Never `2>/dev/null` a convergence poll.** Suppressing stderr converts the failure above — and any `gh`/auth/network/`jq` error — into *false silence*: an empty result that reads exactly like "no findings" and merges the bug unfixed. This is the real-world trigger of every false-convergence variant above. Let the poll's errors print and eyeball them; a convergence check must fail **loud**, never quiet. If you must separate streams, capture stderr and assert it's empty — don't discard it.
- **The clean verdict must name the CURRENT HEAD.** Codex's clean comment prints `Reviewed commit: <sha>`. A PR clean on commit `A` that then receives commit `B` still shows `A`'s verdict — and `B` has no inline findings yet *because Codex hasn't reviewed it*. Pairing those two reads as "converged". **Resolve the explicit `Reviewed commit` SHA (including a unique abbreviated SHA) and compare it to the full PR HEAD; never search the whole body for a HEAD substring.** An unrelated link can mention HEAD while the verdict reviews an older commit. Re-check PR HEAD after collection and before handoff; a changed HEAD invalidates the snapshot.
- Corollary: **never merge on a premature zero.** If you have not seen either a current-HEAD clean verdict or actual current-round findings with a stable, fully triaged snapshot, the review is still in flight.
